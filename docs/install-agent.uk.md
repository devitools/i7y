# Встановлення демона i7y на сервер

Цей посібник описує встановлення `i7y-agent` на сервер Linux із Docker і systemd. Агент запускається під час завантаження системи, збирає дані одразу, а потім кожні п’ять хвилин. Він оновлює стан контейнерів і використовувані образи в i7y та зберігає історію телеметрії.

Агент також відстежує події Docker через локальний сокет. Створення, запуск, зупинка, видалення та зміни справності запускають швидке узгодження стану з групуванням подій протягом двох секунд. Після повторного підключення агент узгоджує стан, відновлюючи пропущені події. Повний збір метрик триває кожні п’ять хвилин; події під час збору обробляються після нього. Видалені контейнери типово приховані; увімкніть Показувати видалені контейнери, щоб їх переглянути. Відкритий список оновлюється кожні десять секунд.

Встановлення не перезапускає та не змінює контейнери застосунків. Для створення користувача й служби агента потрібен адміністративний доступ. Доступ до сокета Docker є привілейованим; використовуйте бінарний файл із надійного джерела та захищайте конфігурацію.

Наведені нижче адреси, користувачі та облікові дані є вигаданими прикладами. Замініть їх значеннями свого середовища.

## 1. Підготовка файлів

На машині з вихідним кодом i7y відкрийте каталог `apps/agent`. За наявності Go зберіть бінарні файли та контрольні суми:

```sh
go test -race ./...
./build.sh
```

Модуль фіксує версію інструментарію. Збірка створює:

- `dist/i7y-agent-linux-amd64`: для 64-бітних серверів Intel/AMD.
- `dist/i7y-agent-linux-arm64`: для 64-бітних серверів ARM.
- `dist/SHA256SUMS`: контрольні суми обох бінарних файлів.

Для запуску агента на цільовому сервері не потрібні Go, Node чи Python. Якщо ви вже отримали бінарні файли з надійного джерела, збірку можна пропустити.

## 2. Перевірка цільового сервера

Підключіться через SSH із правильним портом та ідентифікаційними даними. Перш ніж приймати невідомий сервер, перевірте ключ хоста за допомогою надійного джерела.

```sh
ssh -p 22 operador@server.example.com
uname -m
systemctl --version
docker version
getent group docker
```

Виберіть бінарний файл відповідно до `uname -m`:

| Результат | Бінарний файл |
| --- | --- |
| `x86_64` | `i7y-agent-linux-amd64` |
| `aarch64` або `arm64` | `i7y-agent-linux-arm64` |

Також переконайтеся, що сервер має доступ до i7y через HTTPS:

```sh
curl --fail --show-error https://inventory.example.com/api/health
```

API має повернути HTTP 200. Перед встановленням усуньте проблеми DNS або сертифіката; не вимикайте перевірку TLS.

Цей інсталятор передбачає, що Docker використовує локальний сокет `/var/run/docker.sock` і що група `docker` існує. Інакше адаптуйте службу до свого середовища перед продовженням.

## 3. Створення облікових даних в i7y

1. Увійдіть в i7y зі своїм користувачем.
2. Якщо сервер ще не зареєстрований, додайте його до правильного робочого простору.
3. Відкрийте **Телеметрія** та розгорніть **Налаштування агента**.
4. Виберіть сервер за зареєстрованою назвою та перевірте його IP на екрані **Сервери**.
5. Натисніть **Створити облікові дані** та підтвердьте.
6. Скопіюйте показаний секрет. Він починається з `i7ya_` і відображається лише під час створення.

Використовуйте окремі облікові дані для кожного сервера. Вони прив’язані до вибраного запису й дозволяють лише читати конфігурацію та надсилати телеметрію цього сервера. Це не загальний токен керування API. У прикладах замініть `https://inventory.example.com` URL-адресою своєї інсталяції.

Якщо агент уже встановлено, перед ротацією облікових даних заплануйте оновлення конфігурації: створення нових для того самого сервера негайно скасовує попередні.

## 4. Копіювання файлів

На сервері підготуйте приватний тимчасовий каталог:

```sh
install -d -m 0700 "$HOME/i7y-install"
```

На машині збірки, у каталозі `apps/agent`, скопіюйте файли. У цьому прикладі використовується `amd64`:

```sh
scp -P 22 \
  dist/i7y-agent-linux-amd64 \
  dist/SHA256SUMS \
  deploy/install.sh \
  deploy/i7y-agent.service \
  operador@server.example.com:~/i7y-install/
```

За потреби додайте `-i /path/to/key` до команд SSH і SCP. Не копіюйте приватний ключ на сервер.

На сервері перевірте контрольну суму отриманого бінарного файлу:

```sh
cd "$HOME/i7y-install"
awk '$2 == "i7y-agent-linux-amd64" { print }' SHA256SUMS > selected.sha256
test -s selected.sha256
sha256sum -c selected.sha256
chmod 0755 i7y-agent-linux-amd64
./i7y-agent-linux-amd64 -version
```

Перевірка контрольної суми має повернути `OK`. Для ARM замініть `amd64` на `arm64` у командах.

## 5. Створення приватної конфігурації

На сервері створіть файл з обмеженими правами доступу та відкрийте його в редакторі:

```sh
cd "$HOME/i7y-install"
install -m 0600 /dev/null config.json
vi config.json
```

Заповніть файл, замінивши URL-адресу й токен фактичними значеннями:

```json
{
  "url": "https://inventory.example.com",
  "token": "i7ya_VSTAVTE_OBLIKOVI_DANI_SERVERA",
  "docker_socket": "/var/run/docker.sock",
  "state_dir": "/var/lib/i7y-agent",
  "roots": ["/usr/share/tevun/projects", "/usr/share/tevun"]
}
```

`roots` визначає, де агент шукає проєкти. Використовуйте фізичні шляхи, перевірені командами `readlink -e /projects` і `readlink -e /usr/share/tevun`, адаптуючи приклад до сервера; неіснуючі каталоги ігноруються. Користувач агента повинен мати змогу читати ці каталоги та проходити через них. Не надавайте права запису до файлів застосунків для збирання даних.

Агент також отримує від i7y шляхи зареєстрованих проєктів. Він розкриває символічні посилання, надсилає та зберігає фізичні шляхи в інвентарі й розпізнає каталог Compose у наявному проєкті, зберігаючи зв’язок за відсутності неоднозначності.

Не розміщуйте облікові дані в командах, історії термінала, репозиторіях, знімках екрана чи зверненнях до підтримки. Не виконуйте `cat config.json` у сеансах зі спільним виводом.

## 6. Встановлення та запуск служби

На сервері:

```sh
cd "$HOME/i7y-install"
sudo sh install.sh \
  ./i7y-agent-linux-amd64 \
  ./config.json \
  ./i7y-agent.service
```

Якщо користувача SSH немає в `sudoers`, скористайтеся вже дозволеним адміністративним доступом. Наприклад, увійдіть як root через `su -` і запустіть той самий інсталятор без `sudo`, використовуючи абсолютні шляхи до підготовленого каталогу. Для встановлення агента не потрібно надавати користувачу SSH право sudo.

Інсталятор створює:

| Розташування | Призначення |
| --- | --- |
| `/usr/local/bin/i7y-agent` | Виконуваний файл |
| `/etc/i7y-agent/config.json` | Конфігурація та облікові дані, режим `0600` |
| `/etc/systemd/system/i7y-agent.service` | Служба systemd |
| `/var/lib/i7y-agent` | Постійна черга та блокування процесу |

Він створює системного користувача `i7y-agent`, вмикає автоматичний запуск служби та запускає її. Конфігурація systemd надає службі доступ до групи `docker`.

## 7. Перевірка встановлення

Перевірте службу:

```sh
systemctl is-enabled i7y-agent
systemctl is-active i7y-agent
sudo journalctl -u i7y-agent -n 30 --no-pager
```

Очікувані результати — `enabled` та `active`. Після збору даних журнали мають містити такі повідомлення:

```text
collected 12 containers; errors=0
queue delivered
```

Перший збір може тривати деякий час залежно від кількості контейнерів. Агент збирає дані одразу після запуску; чекати п’ять хвилин до початку не потрібно.

Щоб перевірити автентифікацію та доступ до Docker без надсилання ще одного зразка:

```sh
sudo -u i7y-agent -g docker \
  /usr/local/bin/i7y-agent \
  -config /etc/i7y-agent/config.json \
  -diagnose
```

Діагностика має повідомити `API and Docker available`. Параметр `-g docker` відтворює доступ до групи, який служба отримує через systemd.

В i7y відкрийте **Телеметрія**, виберіть сервер і натисніть **Оновити**. Перевірте:

- Актуальну версію агента й недавній контакт.
- Відповідність списку контейнерів виводу `docker ps -a`.
- Відповідність образів посиланням, налаштованим у фактичних контейнерах.
- Наявність метрик та історії без неочікуваних помилок збору.

Після зміни образу та повторного створення контейнера на сервері наступний збір автоматично оновить поле `image` в інвентарі. Саме лише завантаження образу через `docker pull` не змінює образ наявного контейнера.

Після перевірки видаліть тимчасову копію облікових даних:

```sh
rm -i "$HOME/i7y-install/config.json"
```

Конфігурація, яку використовує служба, залишається в `/etc/i7y-agent/config.json`.

## 8. Оновлення агента

Зберіть або отримайте новий бінарний файл і перевірте його контрольну суму. Створювати нові облікові дані чи перевстановлювати контейнери не потрібно.

Коли новий бінарний файл уже на сервері:

```sh
sudo cp -p /usr/local/bin/i7y-agent /usr/local/bin/i7y-agent.previous
sudo install -m 0755 ./i7y-agent-linux-amd64 /usr/local/bin/i7y-agent.next
sudo mv /usr/local/bin/i7y-agent.next /usr/local/bin/i7y-agent
sudo systemctl restart i7y-agent
/usr/local/bin/i7y-agent -version
sudo journalctl -u i7y-agent -n 15 --no-pager
```

Заміна через перейменування дозволяє не перезаписувати виконуваний файл, який працює. Конфігурація та черга зберігаються. Перевірте нову версію в наступному зразку i7y.

Щоб відновити попередній бінарний файл:

```sh
sudo install -m 0755 /usr/local/bin/i7y-agent.previous /usr/local/bin/i7y-agent.next
sudo mv /usr/local/bin/i7y-agent.next /usr/local/bin/i7y-agent
sudo systemctl restart i7y-agent
```

## 9. Усунення поширених проблем

| Симптом | Перевірка |
| --- | --- |
| `configuration must have mode 0600` | Перевірте права командою `sudo stat /etc/i7y-agent/config.json`. |
| `API HTTP 401` | Перевірте, чи облікові дані належать цьому серверу та чи не були вони відкликані або замінені. |
| `API HTTP 403` | Перевірте правила проксі та Cloudflare для кінцевої точки телеметрії. |
| `API connection failed` | Перевірте DNS, з’єднання HTTPS, сертифікат і URL-адресу в конфігурації. |
| `Docker unavailable` | Перевірте роботу Docker, налаштований сокет і доступ служби до групи `docker`. |
| `project path inaccessible` | Перевірте права читання та проходження каталогів для `i7y-agent`. |
| `another agent is running` | Інший процес використовує ту саму чергу; використовуйте екземпляр, керований systemd. |
| Неоднозначний проєкт або зв’язок | Перевірте шляхи та зв’язки в інвентарі; агент зберігає наявні записи замість непомітного переміщення контейнерів. |
| Немає зв’язку на панелі | Перевірте службу та журнали; панель позначає відсутність контакту через 15 хвилин. |

Під час збою мережі агент зберігає локальну чергу до 24 годин/288 зразків і повторює надсилання зі збільшенням затримки. Сервер розпізнає повторні зразки, щоб не дублювати історію.

Якщо `/projects` є символічним посиланням на каталог у `/home`, перевірте весь шлях командою `namei -l /projects`. Домашній каталог із режимом `0700` блокує доступ, навіть якщо кінцевий каталог доступний для читання. За потреби надайте користувачу агента лише право проходження батьківського каталогу, наприклад `sudo setfacl -m u:i7y-agent:--x /home/operador`. Це не дозволяє переглядати його вміст; каталоги проєктів усе ще мають дозволяти читання, потрібне для виявлення. Перезапустіть лише `i7y-agent` і перевірте наступне надсилання.

## 10. Зупинка або видалення

Щоб тимчасово зупинити:

```sh
sudo systemctl stop i7y-agent
```

Щоб запустити знову:

```sh
sudo systemctl start i7y-agent
```

Щоб видалити службу й бінарний файл, використовуйте `apps/agent/deploy/uninstall.sh` із вихідного коду:

```sh
sudo sh uninstall.sh
```

Скрипт зберігає конфігурацію та чергу. Відкличте облікові дані на екрані телеметрії, якщо сервер остаточно припиняє надсилати дані. Видалення агента не видаляє проєкти чи контейнери з інвентарю та не впливає на фактичні контейнери.
